    **`## Breaking-Change Policy`**
    - Definition: a "breaking" schema change is one that would cause the validator to reject a previously-valid `hierarchy.json` IF a consumer were to upgrade to the new schema while still serving the old data, OR one that changes the meaning of an existing field. Adding a field, adding an optional metadata file, or relaxing a constraint is non-breaking.
    - 30-day advance notice (D-09) for breaking schema changes. Aligns with SPS's existing 30-day schema-change protocol.
    - Notice mechanism: a CHANGELOG entry below with target activation date, AND the new schema is published alongside the existing one at the existing version until the window elapses.
    - Communication: `manifest.schema_version` bumps and the CHANGELOG entry are the canonical records (D-10). No email, no Slack — the manifest sha256 is the signal, the CHANGELOG is the explanation.

    5. Project the validated structure into the consumer's storage layer.
    6. Persist `manifest.sha256` and `manifest.version` so step 2 can short-circuit on the next poll.
