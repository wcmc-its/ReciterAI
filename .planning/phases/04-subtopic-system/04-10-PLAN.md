- `"topic_decompose"` — query routed to Tier 4 renderer
- `"gap_query"` — gap_query dispatcher path; cascade Pass 1 only
- `"team_assembly"` — team_assembly dispatcher path; per-role cascade Pass 1
- `"unsupported"` — router guardrail rejects (similarity, nomination, network) before retrieval

Algorithm:
1. Load golden-queries.json. For each query:
   a. POST to /api/chat with {message: query.query, conversationId: null, mode: <baseline|hierarchy>}
   b. Stream response; collect full text; parse to extract ranked personIdentifiers (topic_match/topic_decompose patterns include them in a structured trailer; for topic_decompose record the subtopic_ids returned instead)
   c. Record returned list + latency + tokens_used.
2. Write all results to --output JSON file.
3. If --diff-report:
   a. Load both baseline_flat_topic_results.json and hierarchy_run_results.json.
   b. For each query_type category, compute mean MRR and mean Recall@10 over queries of that type.
   c. PASS threshold: hierarchy_MRR >= baseline_MRR AND hierarchy_Recall@10 >= baseline_Recall@10 per category.
   d. Write regression_gate_report.md with table:
      | Category | Baseline MRR | Hierarchy MRR | Baseline R@10 | Hierarchy R@10 | Status |
   e. Overall PASS if all 4 categories PASS; exit 0. Otherwise exit 1.

Special handling for topic_decompose queries: expected_faculty is meaningless; instead, the baseline returns nothing (Phase 2 doesn't know topic_decompose) and hierarchy returns structured subtopic list. Measure structural correctness: did the Tier 4 renderer return a non-empty subtopics array with expected parent topic?
