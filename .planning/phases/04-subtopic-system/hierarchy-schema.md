# hierarchy.json Schema (Phase 4 authoritative)

This file is the single source of truth for the `hierarchy.json` JSON shape.
Every Phase 4 plan (Passes 1/2/3, see-also generation, PM loader, Tier 4
renderer) references this schema. Updates to the shape MUST land here first,
then propagate to consumers.

## Location

`ReCiter-Publication-Manager/controllers/chatbot/hierarchy.json`

Committed to the PM worktree on `feature/chatbot-runtime`. Sits alongside
`taxonomy.ts` and `taxonomy_v2.json`. Regenerated by the Python pipeline
(Passes 1/2 + see-also batch) and copied into PM via manual commit, mirroring
the existing `taxonomy_v2.json → taxonomy.ts` workflow (Plan 02-08).

## Top-level shape

```ts
interface HierarchyJson {
  version: "subtopic_v1";                    // string literal
  generated_at: string;                      // ISO 8601 UTC, e.g. "2026-04-15T12:00:00Z"
  taxonomy_version: string;                  // parent taxonomy version, e.g. "taxonomy_v2"
  excluded_topics: ExcludedTopicEntry[];     // topics below cold-start floor (D-01)
  topics: Record<string, TopicEntry>;        // keyed by topic_id (from taxonomy_v2)
  see_also: SeeAlsoEntry[];                  // cross-topic subtopic links (D-08, D-09)
}

interface TopicEntry {
  subtopics: SubtopicDef[];
}

interface ExcludedTopicEntry {
  id: string;
  reason: string;        // e.g. "below cold-start floor"
  activity_count: number;
}
```

## SubtopicDef

```ts
interface SubtopicDef {
  id: string;                 // `{topic_prefix}_{slug(label)}` — NOT stable across recomputes (D-06)
  label: string;              // canonical subtopic name — injected into synthesis prompts (D-15)
  description: string;        // injected verbatim into Tier 1/2 synthesis prompts (D-15)
  display_name: string;       // UI-only Title Case card title (D-19) — never injected into LLM prompts
  short_description: string;  // UI-only noun-phrase tagline, <= 140 chars (D-19)
  activity_count: number;     // display only (D-07) — do NOT use for retrieval thresholds
  total_weight: number;       // retrieval threshold signal (D-07, D-13) — sum of articleScores
}
```
Note: For the published-artifact contract (S3 URL pattern, schema, manifest, cadence, breaking-change policy, CHANGELOG), see `docs/hierarchy-contract.md` (Phase 5). That document is the single consumer-facing reference for any agent integrating against the published `hierarchy.json` artifact.

Key rules:
- **ID instability (D-06):** On recompute, hierarchy is replaced wholesale —
  subtopic IDs may change. No migration logic. Consumers must re-read
  `hierarchy.json` after each regeneration and MUST NOT persist subtopic IDs
  in external systems that outlive a recompute cycle.
- **activity_count vs total_weight (D-07):** `activity_count` is for UI
  display; retrieval tier decisions use `total_weight` so a subtopic with a
  few high-impact/high-relevance blockbuster papers still registers above the
  floor. See `calibration-notes.md` (SUB-17) for the chosen `WEIGHT_FLOOR`
  value.
- **description verbatim (D-15):** Tier 1/2 synthesis prompts inject
  `subtopic.label` and `subtopic.description` character-for-character. Do not
  post-process, summarize, or truncate.
- **UI vs synthesis split (D-19):** `label` and `description` are the
  synthesis-injected fields (D-15). `display_name` and `short_description`
  are UI-facing card strings emitted by Pass 1 Sonnet alongside `label` /
  `description`, with explicit style rules enforced in
  `prompts/subtopic_discovery.py` (Title Case `display_name`, max 6 words,
  ampersands or hyphens for compound concepts; noun-phrase
  `short_description`, <= 140 chars, no "Research on..." / "Studies of..."
  openers). UI consumers MUST prefer `display_name` over `label` and SHOULD
  render `short_description` as the card subtitle. UI consumers MUST
  tolerate empty / missing values: `hierarchy.json` files generated before
  D-19 backfill `display_name` from `label` at assembly time
  (`backfill_all.py`), and `short_description` may be an empty string
  until the next annual recompute. These fields are NEVER injected into
  synthesis prompts — doing so would defeat the design split.
  - **Downstream consumers:** Scholars Profile System (Cornell's VIVO
    replacement) is the primary external consumer. PM chatbot cards are
    a future internal consumer (currently subtopics are not surfaced in
    the PM UI per 04-CONTEXT.md decision; if that changes, the same D-19
    rules apply). When adding a new consumer, follow the SPS integration
    contract: prefer `display_name`, render `short_description` as
    subtitle, tolerate empty values, never pass these fields to an LLM.
  - **Annual recompute is the canonical population path.** `display_name`
    and `short_description` are emitted naturally by Pass 1 discovery
    (`discover_subtopics.py`) on each annual hierarchy regeneration and
    flow through `backfill_topic.py` (which preserves all keys via
    `dict(s)`) into `backfill_all.py`'s SubtopicDef projection.
  - **Out-of-band backfill:** `relabel_subtopics.py` (paired with
    `prompts/subtopic_relabel.py`) provides an idempotent one-shot pass
    that adds the two UI fields to existing
    `hierarchy_draft_<id>.json` and `hierarchy_augmented_<id>.json`
    files WITHOUT re-running clustering, WITHOUT changing IDs (preserves
    D-06 stability), and WITHOUT touching `label`, `description`,
    `seed_pmids`, `total_weight`, or `activity_count`. CLI:
    `python relabel_subtopics.py [--topic ID] [--limit N] [--force]
    [--dry-run]`. Idempotent by design: subtopics with both fields
    already populated are skipped unless `--force` is passed. Use only
    when UI fields need to land before the next annual recompute. After
    running, re-assemble `hierarchy.json` via
    `python backfill_all.py --assemble-only [--skip-pm-copy]` — this
    skips Pass 1/2/3 and see-also generation, calls no LLM, and
    inherits `excluded_topics` + `see_also[]` from the prior
    `hierarchy_full.json` (subtopic IDs are stable per D-06, so the
    existing see-also network remains valid). Sub-second runtime.

## SeeAlsoEntry

```ts
interface SeeAlsoEntry {
  from: string;    // source subtopic id (may be a subtopic id OR a topic id for topic-level links)
  to: string;      // target subtopic id
  reason: string;  // one-sentence Sonnet-generated rationale
}
```

Bidirectionality rule (D-09): **Both `(A, B)` and `(B, A)` entries must be
present after the bidirectionality filter.** The see-also generator emits
directed proposals; the filter retains a link only if both directions were
independently proposed in the same run (or in a temperature=0 re-run). Links
that survive are written symmetrically.

## Legacy tolerance (D-18)

Absent subtopic fields on a DynamoDB record mean **unassigned**, not error.
Every reader (Phase 2 retrieval, PM loader, Tier 3 fallback) MUST use `??
default` coercion:

```ts
// Phase 2 pattern — reference shared.ts:220-237
const subtopicIds: string[] = item.subtopic_ids ?? [];
const primarySubtopic: string | null = item.primary_subtopic_id ?? null;
const subtopicConfidences: Record<string, number> = item.subtopic_confidences ?? {};
```

Topics that have never been through Pass 1 will permanently lack subtopic
fields. Retrieval falls back to Tier 3 (topic-level) for these.

## Excluded topics rule (D-01)

Topics with fewer than 30 qualifying activities ("cold-start floor") are NOT
run through Pass 1. They are listed in the top-level `excluded_topics[]`
array with `reason: "below cold-start floor"` and their `activity_count`.

Consumers that receive a `topic_decompose` query against an excluded topic
use this array to emit the partial/fallback UX per SUB-16:

> "Hierarchy pending for \<topic\>; falling back to topic-level results."

## Decision references

- **D-01** Cold-start floor (30 activities) → `excluded_topics[]`
- **D-06** No stable subtopic IDs — wholesale replacement on recompute
- **D-07** Dual metrics: `activity_count` (display) vs `total_weight` (threshold)
- **D-09** Bidirectionality filter on see-also links
- **D-13** `total_weight` is the retrieval threshold signal (v1 assumption pending calibration per SUB-17)
- **D-15** Synthesis prompts inject subtopic label + description verbatim
- **D-18** Legacy tolerance: absent fields = unassigned state
- **D-19** `display_name` + `short_description` added as non-breaking additive fields for SPS card rendering
