# G-37 — Bounded E2E Integration Test for the Cold Path

## Context

G-37 is one bounded E2E integration test per D-21. D-19 carves it out as a separately-gated final task within Phase 12 (per D-20) because it is the only §11 residual item with a design problem before it is a coding problem: what does a representative fixture corpus look like? The other five §11 items (G-1, G-18, G-24, G-34, G-36) are mechanical or writing tasks and ship inside the main phase work. G-37 is the only one that requires designing the fixture before writing the test.

D-22 requires this tracking issue to be filed from the first commit of Phase 12 so that "if G-37 slips, the issue is already filed with the correct context" — same pattern as Phase 11's cutover audit rows (make carry-forward state queryable from day one).

## Gating Contract

Per D-20, G-37 work starts only after `pytest` exits 0 on every other Phase 12 deliverable on `main`. The SHA is captured at gate time:

```bash
GATE_SHA=$(git rev-parse main)
pytest tests/test_thresholds_schema.py tests/test_thresholds_keys.py \
       tests/test_env_check_thresholds.py tests/test_stage_records.py \
       tests/test_critic_reject_event.py tests/test_critic_reject_producer.py \
       tests/test_pipeline_drift_evaluator.py tests/test_aggregate_inclusive.py \
       tests/test_aggregate_idempotent.py tests/test_reconciliation_gate.py \
       tests/test_rollup_incremental_parity.py tests/test_feedback_finding_records.py \
       tests/test_feedback_sweep.py tests/test_feedback_cli.py \
       tests/test_feedback_render.py tests/test_hierarchy_reproducibility.py -x
```

"Gated on the feedback work being merged" is too vague — it can mean "the PR is open and looks fine," which is exactly how integration testing gets started against half-stable substrate and produces tests that drift the moment something lands (D-20 SHA-able gating rationale).

## Deliverable

Per D-21, the G-37 deliverable is **one specific bounded E2E test** — not a general test suite:

> Run a stripped-down fixture corpus through the cold path from `generate_taxonomy.py` to `pipeline_hierarchy/publish.py`, assert the published manifest validates against the published schema, assert the same fixture corpus produces a byte-identical `hierarchy.json` on a second run (Phase 11 G-29 removed the timestamp fields that previously broke this invariant).

This is not "an integration test against fixtures" in general — it is one test that buys the most architectural confidence per unit of work. Additional integration tests are follow-ups.

The byte-identical second-run invariant is meaningful because Phase 11 G-29 shipped: `pipeline_hierarchy/generator.py:47` removed `generated_at` from `hierarchy.json`, making the output deterministic.

## Fixture Corpus Shape

Per PATTERNS.md (Pitfall 4): **plan the fixture corpus shape before writing the test code**. The corpus must be small enough to run end-to-end in <60s but large enough to exercise every cold-path stage.

Target shape: **2 topics × 3 subtopics × 5 pubs = 30 pubs**

- 2 topics: exercises topic-level iteration logic without requiring a full taxonomy.
- 3 subtopics per topic: exercises subtopic assignment branching (primary selection, tie-breaking, multi-assignment).
- 5 publications per subtopic assignment: sufficient for spotlight to have candidates; small enough for fast fixture load.

Fixture location: `tests/fixtures/cold_path_e2e/` with a `README.md` documenting the corpus shape and why it was chosen.

The fixture shape must be documented in the test docstring before the test is written (RESEARCH Pitfall 4: "define the fixture corpus shape explicitly in the test plan before writing test code").
